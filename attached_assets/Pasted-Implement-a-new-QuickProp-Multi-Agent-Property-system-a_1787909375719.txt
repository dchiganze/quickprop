Implement a new QuickProp “Multi-Agent Property” system across the existing shared backend, CRM and website. This must be a clean MVP implementation with production-ready architecture, not a separate prototype. Preserve all existing QuickProp functionality and styling.

CORE PRINCIPLE:
One physical property = ONE canonical property record. Multiple registered estate agents/agencies can be associated with that same property without creating duplicate search results. Each agent retains their own marketing relationship, price, terms, description and media attribution.

1. DUPLICATE DETECTION BEFORE LISTING CREATION
When an agent begins uploading a property, perform duplicate detection BEFORE creating the new property record.

Compare:
- normalized address
- suburb/location
- GPS coordinates where available
- property type
- bedrooms/bathrooms
- land/building size
- price
- description similarity
- phone/contact information where appropriate
- image similarity where possible

Return a confidence score.

If a likely duplicate is detected, show a professional modal:

“Possible existing property detected”

14 Borrowdale Brooke
4 bedrooms • 3 bathrooms • 2,000 sqm
Currently listed by ABC Properties
Current asking price: US$475,000
Last verified: 4 days ago

“Is this the same property?”

[ YES — ADD MY AGENCY ]
[ NO — CREATE NEW PROPERTY ]
[ I’M NOT SURE ]

Do NOT block the agent unnecessarily. If they select “I’m not sure”, allow the upload to continue but flag it for admin duplicate review.

Use sensible confidence thresholds:
- >95% = high-confidence duplicate
- 80–95% = possible duplicate
- <80% = do not interrupt the upload unless other strong signals exist

2. ONE CANONICAL PROPERTY RECORD
Create a single canonical Property entity/record with a unique Property ID.

Store common physical property information once:
- address
- location/suburb
- GPS
- property type
- bedrooms
- bathrooms
- land size
- building size
- features
- property status
- canonical property history
- duplicate/merge history

Do NOT create a second property record simply because another agency markets it.

3. MULTIPLE AGENT RELATIONSHIPS
Create a separate PropertyAgentRelationship / AgencyListing relationship.

A property can have multiple authorised agents/agencies.

Each relationship should contain:
- agent
- agency
- mandate type: Sole / Exclusive, Non-exclusive, Collaboration
- relationship status
- date added
- verification status
- asking price
- price status
- terms
- agent-specific description
- agent-specific contact details
- agent-specific marketing assets
- last availability confirmation
- last update
- collaboration information if applicable

4. DIFFERENT PRICES AND TERMS
Do NOT force multiple agents to use one price.

Example:

ABC Properties
US$475,000
Cash / Negotiable

XYZ Realty
US$450,000
Terms Accepted

These are separate agent offers against the SAME canonical property.

On the consumer page display:
“From US$450,000”
and clearly show the individual agent offers and terms.

Flag significant price discrepancies internally for admin review rather than automatically overwriting one agent’s price.

5. MARKETING ASSET OWNERSHIP AND ATTRIBUTION
Each agent retains ownership/attribution of their uploaded:
- photos
- videos
- descriptions
- floorplans
- marketing content

All approved agency photos may be displayed on the canonical property page.

Every photo must have a subtle professional agency watermark/attribution overlay, e.g.:
“ABC PROPERTIES”

Do not make the watermark intrusive.

Store which agency uploaded each asset and never silently transfer asset ownership when properties are merged.

8. “ADD MY AGENCY” FLOW
When an agent confirms a detected duplicate:

Show:

“This property already exists on QuickProp.”

“Add your agency to the existing property?”

[ CONTINUE ]

Then collect:
- mandate type
- asking price
- terms
- agent-specific description
- photos/media
- agent contact details

Clearly explain:
“Your agency will be added to the existing property. Your price, terms and marketing content will remain attributed to your agency.”

Make this a maximum 2–3 step process.

9. “I’M NOT SURE” FLOW
If the agent selects “I’m not sure”:

Allow them to continue.

Create a “Potential Duplicate” admin flag containing:
- both property records
- duplicate confidence score
- matching fields
- images for comparison
- agencies involved

Admin can later:
[ MERGE ]
[ KEEP SEPARATE ]
[ REQUEST INFORMATION ]

10. ADMIN MERGE / UNMERGE
Add functionality to the QuickProp Admin Portal.

Admins can:
- view potential duplicates
- compare properties side-by-side
- compare photos
- compare agencies
- compare prices
- merge duplicate property records
- keep records separate
- unmerge a mistaken merge

When merging:
- select canonical property record
- preserve ALL agent relationships
- preserve ALL marketing assets and attribution
- preserve enquiries/leads
- preserve analytics
- preserve property history
- preserve audit trail

Never delete historical information.

15. SHARED ARCHITECTURE
This must use the EXISTING QuickProp shared backend/database/API used by:
- QuickProp Agent Mobile App
- QuickProp CRM
- QuickProp Website
- QuickProp Admin Portal

Do not create a separate database or isolated mock backend.

Ensure changes made in the CRM appear on the website and mobile app, and vice versa, through the shared canonical property record.

Use reusable components and APIs so the same property data model is used everywhere.

16. MOBILE-FIRST UX
The agent upload and duplicate detection flow must be extremely fast and mobile-friendly.

An agent should be able to:
Upload → detect duplicate → confirm relationship → add price/photos → publish

with minimal typing and no unnecessary screens.

The entire experience should feel like QuickProp is helping the agent rather than creating additional administration.

IMPORTANT:
Do not over-engineer the interface. Prioritise speed, clarity, trust, duplicate prevention and ease of use.

Build the database/schema, backend logic, API endpoints, frontend components and demo data required for this feature. Ensure existing QuickProp functionality is not broken.
